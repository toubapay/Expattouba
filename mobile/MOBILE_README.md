# SeneMarket mobile (Flutter)

Native/web client for the same Expattouba backend the React app
(`../src`) talks to — same API, same accounts, same wallet and vendor
plans. This folder was **hand-written**, not generated by `flutter
create`: there is no Flutter/Dart SDK in the environment that produced
it, so none of this has been run, compiled, or `flutter analyze`'d.
Treat it as a careful port that needs a first real build to shake out
whatever the compiler would have caught — likely candidates are minor
API drift in Flutter/package versions (an `initialValue` vs `value`
kind of mistake), not architecture.

## What's here vs. what you need to generate

Everything under `lib/`, `web/`, and `pubspec.yaml` is safe hand-written
Dart/config and is included. What's **not** here, on purpose: the native
Android and iOS project scaffolding (`android/`, `ios/`) — Gradle
wrapper files, `.pbxproj`, plist boilerplate. Those are fragile,
mostly-generated formats where a hand-authored copy is more likely to be
subtly wrong than absent, with no compiler here to catch it. Generate
them instead:

```bash
cd mobile
flutter create --platforms=android,ios,web --org com.senemarket --project-name senemarket .
```

This creates `android/`, `ios/`, and its own `web/` next to the existing
`lib/` and `pubspec.yaml` **without touching them** — except it will
also drop its own default `web/index.html`, `web/manifest.json`, and
`web/icons/`. Re-apply the ones from this folder afterward (they carry
the SeneMarket branding and theme color; the generated `web/icons/*.png`
placeholders are fine to keep as-is until you have real app icons):

```bash
git diff --stat web/index.html web/manifest.json   # confirm what flutter create overwrote
git checkout -- web/index.html web/manifest.json   # restore the ones from this repo
```

Then:

```bash
flutter pub get
```

## Running it

**Web** (works today, no extra setup — this is the fully-supported
target):

```bash
flutter run -d chrome
```

On web, `ApiConfig.baseUrl` (`lib/services/api_client.dart`) resolves to
an empty string on purpose — requests go to whatever origin serves the
Flutter build, mirroring how `server.ts` serves the React SPA and the
API from one process. Running via `flutter run -d chrome` (its own dev
server, not the backend's) means API calls will 404 unless you also pass
the backend's origin:

```bash
flutter run -d chrome --dart-define=API_BASE_URL=http://localhost:3000
```

For a production web build, build and deploy the output as a static
site pointed at the real backend origin, or drop the build output behind
the same origin as the backend (then the empty-string default is
correct and no `--dart-define` is needed):

```bash
flutter build web --dart-define=API_BASE_URL=https://your-app.onrender.com
```

**Android / iOS** (needs the scaffolding step above, plus real devices
or emulators/simulators — neither exists in the sandbox that wrote this
code, so this path is completely untested):

```bash
flutter run --dart-define=API_BASE_URL=https://your-app.onrender.com
```

`API_BASE_URL` is **required** on native — there's no "same origin" to
fall back to on a phone. Leaving it off is a loud failure (every request
hits a relative path with nothing behind it), which is deliberate: it's
better than silently pointing at the wrong server.

## Google Sign-In is web-only for now

`lib/firebase_options.dart` only fills in the `web` config (copied from
the React app's own `firebase-applet-config.json` — same Firebase
project, so a Google login from either client lands the same account).
Android and iOS need their own config files from the Firebase console,
which nothing in this sandbox can generate:

1. Firebase console → Project settings → your `ocass-8e158` project →
   Add app → Android (and separately, iOS).
2. Android: download `google-services.json`, place it at
   `android/app/google-services.json`. You'll also need the Google
   Services Gradle plugin wired into `android/build.gradle` and
   `android/app/build.gradle` — the `flutter create` output doesn't add
   this by default; `flutterfire configure` (once you have the Firebase
   CLI available) does this correctly in one step and is the easier
   path than hand-editing Gradle files.
3. iOS: download `GoogleService-Info.plist`, add it to the Xcode project
   (`ios/Runner/GoogleService-Info.plist`, added via Xcode so it's
   registered in the project, not just copied to disk).
4. Once both exist, fill in `DefaultFirebaseOptions.currentPlatform`'s
   `android`/`ios` cases in `lib/firebase_options.dart` (currently they
   throw `UnsupportedError` on purpose, so a missing config fails loudly
   instead of silently misrouting auth).

Until then, `AuthService.signInWithGoogle()` throws a friendly
French-language error on non-web platforms and `auth_screen.dart` hides
the Google button outside `kIsWeb`. **Phone/PIN auth needs none of this
and already works on every platform** — it's just a JSON POST to the
same backend the web app uses.

## Paydunya checkout return flow differs by platform

Buying a vendor plan opens a hosted Paydunya checkout page
(`lib/screens/profile/vendor_plans_screen.dart`). Getting back into the
app after paying works differently per platform and both paths are
already wired up:

- **Web**: a full-page redirect (`webOnlyWindowName: '_self'`) —
  Paydunya's `return_url`/`cancel_url` point back at this same app, so
  the page reloads and `app_shell.dart`'s `_handlePaydunyaReturn()`
  reads `Uri.base.queryParameters['vendorPlanOrder']` on startup and
  syncs the order status.
- **Native**: opens in an external browser tab
  (`LaunchMode.externalApplication`) since there's no deep link
  registered back into the app. `vendor_plans_screen.dart` instead
  watches `WidgetsBindingObserver.didChangeAppLifecycleState` and syncs
  the pending order when the user switches back to the app after paying
  or cancelling. This is a reasonable UX but untested against a real
  device — if you want a cleaner native return (auto-opening straight
  back to the confirmation), register a custom URL scheme or App
  Link/Universal Link and pass it as Paydunya's `return_url` instead.

Either way, the client **never trusts the redirect by itself** — it
always calls the backend's sync endpoint, which re-verifies the payment
server-to-server with Paydunya before activating anything. See
`backend/src/lib/paydunya.ts`'s own doc comment for the caveat that the
Paydunya integration itself is architecturally sound but unverified
against a live account (no network egress to paydunya.com from the
sandbox that wrote it).

## First things to check once you can actually build this

Nothing here has run through a compiler. In rough order of "most likely
to actually be wrong":

1. `flutter pub get` dependency resolution — version constraints in
   `pubspec.yaml` are caret ranges around what was current when this was
   written, not pinned exact versions; widen anything that fails to
   resolve.
2. `flutter analyze` — check for API drift (wrong named parameter, a
   renamed method) in each Material widget usage. Two spots already
   flagged as guesses in the code itself:
   `post_listing_screen.dart`'s `DropdownButtonFormField` and any
   `Color.withValues(alpha:)` calls (newer Flutter API — if your SDK is
   older, these need to be `.withOpacity()` instead).
3. Image handling — the backend stores listing photos as base64 `data:`
   URIs, not regular URLs; `lib/widgets/listing_image.dart` branches on
   that already, but it's worth confirming against a real photo from the
   backend.
4. Everything Paydunya- and Google-Sign-In-related, per the two sections
   above — both are architecturally complete but genuinely unverified.

## Feature parity with the web app

This client was brought up to date with two rounds of web changes made
after it was first written: categories with structured fields
(Immobilier/Véhicules/Emploi — `lib/theme/category_fields.dart`),
city/price/text search (`lib/screens/home/home_screen.dart`), favorites
(`lib/services/favorites_repository.dart`,
`lib/screens/profile/favorites_screen.dart`), and the redesigned home
feed (compact horizontal rows on a narrow screen, spec chips, quick
call/WhatsApp buttons, a VEDETTE badge on every featured card, real
relative dates). Every request/response shape this update relies on was
cross-checked directly against the actual Express routes and Drizzle
schema (not written from memory) — but the *rendering* of it, same as
everything else in this app, has not been seen by a Flutter compiler.
Two spots most worth a first look once you can build this:

- `home_screen.dart`'s compact row card uses a fixed `childAspectRatio:
  2.9` in the `SliverGrid` to budget its height (title, chip, location/
  date, price+contact row) — if a long title or an unusually large spec
  chip pushes past that on a real device, this is the number to adjust.
- `product_detail_screen.dart`'s attribute grid sizes each box off a
  `LayoutBuilder` rather than the screen width specifically so it stays
  correct inside the 640px-capped wide layout — worth confirming both
  breakpoints render without overflow.
